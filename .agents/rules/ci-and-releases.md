# CI and releases

- `.github/workflows/pipeline.yml` runs on every push with top-level `permissions: {}`; each job grants only what its reusable workflow needs. The other workflows (`mirror-and-archive.yml`, `issue-pull.yml`, `collaborators-only.yml`) are repository housekeeping and stay as they are.
- Branch pushes run `code` (`make lint`, `make test`) and then `code-arm64` (`make test-integration` on `ubuntu-24.04-arm`). `code-arm64` must keep `needs: [code]`: both call `code-workflow.yml`, which takes its concurrency group from the caller's workflow, event and ref, so concurrent calls cancel each other.
- `call-docker-image-workflow` needs both code jobs. On `main` it builds `linux/amd64,linux/arm64` and pushes `psyb0t/reverse-engineer-anything:latest` and `:sha-<commit>` (`push_sha_tag: true`). Keep `scan_fail_build: false`: Grype findings go to the Security tab, and a failed scan must not block a tag from promoting the build.
- A `v*` tag never rebuilds or retests. `wait` waits for the `main` run of the tagged commit, `docker-promote` re-points the release tag at its `sha-<commit>` image (`promote_on_tag: true`, `create_release: false`), `release` cuts the GitHub release from the annotated tag message, then ClawHub and the MCP registry publish. A release tag therefore goes on a commit whose `main` pipeline run passed.
- Versions change only through `make version V=X.Y.Z`, which writes `VERSION` and `.agents/.codex-plugin/plugin.json`.
